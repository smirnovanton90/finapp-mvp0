**Версия:** 1.1  
**Дата:** 31.01.2026  
**Роль:** Senior бизнес-аналитик

## 1. Анализ предложенной постановки

### 1.1 Исходные требования (кратко)

- Убрать из списка активов и обязательств виды «Долги третьих лиц» и «Долги третьим лицам».
- Ввести вид «Взаиморасчёты»: создаётся только автоматически при первой транзакции «Долги» с контрагентом, недоступен для ручного создания; при положительном остатке — в активах, при отрицательном — в обязательствах (аналогично кредитной карте).
- Одна кнопка создания транзакции, разрезанная на две части: «Простая транзакция» (основная) и «Специальная транзакция» (узкая, с иконкой).
- Простая транзакция: доход, расход, перевод.
- Специальная транзакция: «Погашение кредитов» и «Долги».
- Транзакция «Долги»: селектор «Я заплатил» / «Заплатили мне», дата, актив/обязательство, контрагент (обязательно), сумма, без категории, комментарий. В результате создаётся перевод; при первом «Долги» с контрагентом автоматически создаётся item «Взаиморасчёты» по этому контрагенту.

### 1.2 Согласованные решения

1. **Миграция:** старые типы «Долги третьих лиц» и «Долги третьим лицам» скрыть из выбора при создании новых активов/обязательств; новый сценарий «Долги» и тип «Взаиморасчёты» вводить только для новых операций. Перенос существующих данных не делаем.
2. **Кнопка:** одна кнопка, визуально разрезанная на две части: первая (основная по ширине) — «Простая транзакция», вторая (узкая) — «Специальная транзакция» с иконкой (без текста или с кратким текстом по дизайну). По клику на первую часть открывается форма простой транзакции (Доход / Расход / Перевод), по клику на вторую — меню или форма выбора «Погашение кредитов» / «Долги».
3. **Плановые операции «Долги»:** поддерживать; правила дат — как для обычных плановых транзакций.
4. **Карточка «Взаиморасчёты»:** редактирование и удаление актива «Взаиморасчёты» для пользователя недоступно. При нулевом балансе карточка автоматически переходит в статус «Закрыта»; при появлении снова задолженности по данному контрагенту — автоматически возвращается в активный статус.
5. **Создание «Взаиморасчётов»:** один item «Взаиморасчёты» создаётся под каждого контрагента в момент первой транзакции «Долги» с этим контрагентом.

### 2.2 Кредитная карта (эталон для «Взаиморасчётов»)

- **Модель:** `Item` с `type_code = 'bank_card'`, `card_kind = 'CREDIT'`. В БД допускаются отрицательные `initial_value_rub` и `current_value_rub` только для этой комбинации (CheckConstraint в `models.py`).
- **Отображение:** `frontend/lib/item-utils.ts` — `getEffectiveItemKind(item, balanceCents)`: для кредитной карты при `balanceCents < 0` возвращается `"LIABILITY"`, иначе `"ASSET"`. Остальные типы используют `item.kind`.
- **Dashboard/активы:** группировка по «актив/обязательство» делается через `resolveItemEffectiveKind` → `getEffectiveItemKind`, поэтому кредитка с минусом уходит в обязательства.

Для «Взаиморасчётов» нужно аналогичное поведение: один тип, хранится как один kind (ниже предлагается ASSET), но при отображении и группировке считать вид по знаку баланса.

### 2.3 Транзакции и форма

- **Направления:** `INCOME`, `EXPENSE`, `TRANSFER` (backend: `TransactionDirection`, frontend: то же).
- **Создание транзакции:** одна кнопка «Добавить транзакцию» открывает `FormModal`; внутри — селектор вида: Доход / Расход / Перевод / **Погашение кредитов** (`formMode === "LOAN_REPAYMENT"`). Тип `TransactionFormMode = "STANDARD" | "LOAN_REPAYMENT"` (`transactions/page.tsx`).
- **Погашение кредитов:** при выборе «Погашение кредитов» — два селектора (актив для списания, обязательство), сумма общая + сумма процентов, категория обязательна. Создаются две транзакции: EXPENSE (проценты, с категорией) и TRANSFER (тело долга, на обязательство).
- **Контрагент:** для доходов/расходов — опционально; для перевода — не выбирается (есть только «корреспондирующий актив»). Для «Долги» контрагент обязателен и определяет, с каким «Взаиморасчётами» работать.

### 2.4 Отчёт «Взаиморасчёты с контрагентом»

- **Файл:** `frontend/app/(app)/reports/counterparty-settlements/page.tsx`.
- **Логика:** по выбранному контрагенту отбираются активы/обязательства с `type_code` из списка «долги третьих лиц / третьим лицам» (`third_party_receivables`, `third_party_payables`). По транзакциям с этими item строится сальдо и движения.
- После рефакторинга источником сальдо должны стать единые «Взаиморасчёты» по контрагенту (один тип, один item на контрагента).

### 2.5 Прочее использование «долговых» типов

- `THIRD_PARTY_DEBT_TYPES`, `THIRD_PARTY_LOAN_TYPES`, `MANDATORY_COUNTERPARTY_TYPE_CODES`, `OPTIONAL_COUNTERPARTY_TYPE_CODES` в `assets/page.tsx` — фильтры, обязательность контрагента, подсказки.
- `item_plan_service.py`: `LOAN_ASSET_TYPES`, `LOAN_LIABILITY_TYPES` — планы погашения и цепочки.
- «Взаиморасчёты» не должны участвовать в планах погашения и в цепочках как кредиты; они только результат переводов «Долги».

## 3. Подробная постановка изменений и доработок

### 3.1 Новый тип актива/обязательства «Взаиморасчёты»

#### 3.1.1 Идентификация типа

- **Предлагаемый `type_code`:** `counterparty_settlements` (латиница в коде, в UI — «Взаиморасчёты»).
- **Kind в БД:** всегда `ASSET` (как у кредитной карты). Разрешение отрицательного баланса задаётся на уровне модели и отображения.

#### 3.1.2 Backend

1. **Модель `Item` (`backend/models.py`)**  
   - Расширить CheckConstraint для отрицательного баланса: разрешить отрицательные `initial_value_rub` и `current_value_rub` не только для `(type_code = 'bank_card' AND card_kind = 'CREDIT')`, но и для `type_code = 'counterparty_settlements'`.  
   - Вариант формулировки:  
     `(initial_value_rub >= 0) OR (type_code = 'bank_card' AND card_kind = 'CREDIT') OR (type_code = 'counterparty_settlements')`  
     и то же для `current_value_rub`.  
   - Миграция: новая миграция Alembic с изменением ограничений.

2. **Создание item**  
   - Запретить пользователю создавать item с `type_code = 'counterparty_settlements'` через обычный `POST /items`: в `main.py` в `create_item` в начале проверять `payload.type_code` и при `counterparty_settlements` возвращать 400 с сообщением, что этот тип создаётся только системой.  
   - Либо вынести создание «Взаиморасчётов» в отдельный внутренний сервис/эндпоинт (например, `ensure_counterparty_settlements_item(user_id, counterparty_id)`), вызываемый при создании транзакции «Долги». Тогда в публичном `POST /items` — запрет на `counterparty_settlements`.

3. **Справочники и валидация**  
   - В `schemas.py` в валидаторах `ItemCreate` при необходимости явно учесть `counterparty_settlements` (например, не требовать для него полей займов/карт и т.д.), либо не включать его в списки типов, доступных пользователю, и обрабатывать только во внутреннем создании.  
   - В `item_opening_service.py` добавить `counterparty_settlements` в `ITEM_TYPE_LABELS` с подписью «Взаиморасчёты».  
   - В `main.py`: для `counterparty_settlements` при автоматическом создании item обязателен `counterparty_id`; в `_MANDATORY_COUNTERPARTY_TYPE_CODES` можно добавить `counterparty_settlements` только если этот тип где-то создаётся через общий контур (иначе — только во внутреннем методе).

4. **Автосоздание «Взаиморасчётов»**  
   - «Взаиморасчёты» создаётся под каждого контрагента **в момент первой транзакции «Долги»** с этим контрагентом.  
   - Реализовать функцию (например, в `transactions.py` или в новом модуле `counterparty_settlements.py`): по `user_id`, `counterparty_id`, `currency_code` (например, RUB) проверить, есть ли уже item с `type_code = 'counterparty_settlements'` и `counterparty_id = counterparty_id`. Если нет — создать item: kind=ASSET, type_code=counterparty_settlements, name="Взаиморасчёты: {имя контрагента}", counterparty_id, open_date=дата начала учёта или текущая, initial_value_rub=0, без полей карты/займа/депозита.  
   - Уникальность: один актив «Взаиморасчёты» на пару (user, counterparty). При необходимости — уникальный индекс/ограничение (user_id, counterparty_id, type_code) для type_code = 'counterparty_settlements'.

5. **Авто-закрытие и авто-открытие карточки «Взаиморасчёты»**  
   - После пересчёта баланса item с `type_code = 'counterparty_settlements'`: если `current_value_rub == 0` — проставить `closed_at` (или иной признак «Закрыта» по модели приложения); если `current_value_rub != 0` — снять закрытие (`closed_at = NULL`).  
   - Вызывать эту логику при сохранении/удалении транзакций, затрагивающих данный item (primary_item_id или counterparty_item_id), либо при общем пересчёте балансов.  
   - Запрет редактирования/удаления: в эндпоинтах обновления и удаления item (PATCH/DELETE) проверять `type_code`; для `counterparty_settlements` возвращать 400 с сообщением, что этот актив управляется системой.

#### 3.2.2 Режимы формы

- «Специальная транзакция» — при клике на узкую часть открывается меню «Погашение кредитов» / «Долги», затем форма в выбранном режиме (LOAN_REPAYMENT или DEBTS).

### 3.3 Специальная транзакция «Долги»

#### 3.3.1 Поля формы

- **Селектор «Я заплатил» / «Заплатили мне»** (обязательный). Влияет на направление перевода (см. ниже).
- **Дата транзакции** (обязательная).
- **Актив или обязательство** (обязательный) — счёт/актив пользователя, с которого или на который идёт движение. Только «обычные» активы/обязательства (без «Взаиморасчётов» и без привязанных карт к счёту, по текущей логике).
- **Контрагент** (обязательный). По нему определяется или создаётся item «Взаиморасчёты».
- **Сумма** (обязательная, > 0).
- **Категория** — не выбирается, не передаётся.
- **Комментарий** — по желанию.

Валюту брать с выбранного актива/обязательства; при несовпадении валюты «Взаиморасчётов» и выбранного счёта — либо запретить, либо конвертация по текущим правилам приложения (если есть).

#### 3.3.2 Логика создания транзакции

1. Пользователь выбирает контрагента и остальные поля.
2. На backend при создании транзакции «Долги» (отдельный эндпоинт или флаг в теле запроса):  
   - По `counterparty_id` и текущему пользователю вызвать `ensure_counterparty_settlements_item` (или аналог): получить или создать item «Взаиморасчёты» с этим `counterparty_id`, в валюте выбранного актива.  
   - Сформировать одну транзакцию с `direction: "TRANSFER"`, `category_id: null`:
     - **«Я заплатил»:** `primary_item_id` = выбранный пользователем актив/счёт (источник), `counterparty_item_id` = id «Взаиморасчётов», `amount_rub` = сумма. То есть списание с выбранного счёта, зачисление на «Взаиморасчёты».
     - **«Заплатили мне»:** `primary_item_id` = id «Взаиморасчётов», `counterparty_item_id` = выбранный пользователем актив/счёт (получатель), `amount_rub` = сумма. То есть списание с «Взаиморасчётов», зачисление на выбранный счёт.
   - `counterparty_id` в транзакции можно проставлять для отчётности (как у доходов/расходов).
   - `transaction_type` — **ACTUAL или PLANNED** по текущим правилам формы (плановые операции «Долги» поддерживаются).
   - `comment` — из формы.

3. Реализация на backend: либо расширить `POST /transactions` (например, тело с `special_kind: "DEBTS"`, `debt_direction: "I_PAID" | "THEY_PAID"`, `counterparty_id`, остальные поля как у перевода), либо отдельный `POST /transactions/debts`. Предпочтительно один эндпоинт с явным типом операции, чтобы одна точка валидации и создания «Взаиморасчётов».

4. На frontend: при режиме DEBTS не вызывать общий `createTransaction` с ручной подстановкой primary/counterparty; вызывать новый метод API (или тот же с полем `special_kind: "DEBTS"`), передавая направление «Я заплатил»/«Заплатили мне», контрагент, выбранный item, дату, сумму, комментарий. Категорию не отправлять.

#### 3.3.3 Валидация

- Контрагент обязателен; актив/обязательство обязательно; сумма > 0; дата не раньше даты начала учёта и не раньше даты открытия выбранного item (и при автосоздании «Взаиморасчётов» — не раньше даты открытия этого item).  
- Проверка достаточности средств: для «Я заплатил» — на выбранном активе (или обязательстве с положительным балансом, если такое возможно) достаточный остаток; для «Заплатили мне» — на «Взаиморасчётах» по контрагенту (допускается отрицательный остаток по правилам типа).  
- Для плановых «Долги» — те же правила дат, что и для остальных плановых транзакций (например, дата не раньше текущего дня при создании плановой).

### 3.4 Отчёт «Взаиморасчёты с контрагентом»

- Источник данных: вместо нескольких item с типами «Долги третьих лиц» и «Долги третьим лицам» использовать один тип `counterparty_settlements`.  
- По выбранному контрагенту находить item с `type_code = 'counterparty_settlements'` и `counterparty_id = id контрагента`. Если такого нет — показывать сообщение «По выбранному контрагенту нет взаиморасчётов» (или «нет операций»).  
- Логика сальдо и движений остаётся: все транзакции, где primary или counterparty — этот item «Взаиморасчёты», и считать дельты по тем же правилам (TRANSFER: primary отдаёт / counterparty получает и т.д.).  
- Тексты в UI заменить с «Долги третьих лиц» / «Долги третьим лицам» на «Взаиморасчёты».

### 3.5 Миграция существующих данных

- **Согласовано:** миграцию данных не делаем. Старые типы «Долги третьих лиц» и «Долги третьим лицам» скрываем из выбора при создании новых активов/обязательств. Существующие item с этими типами остаются в системе и отображаются как раньше (для обратной совместимости). Отчёт «Взаиморасчёты с контрагентом» после доработки строит данные по типу `counterparty_settlements`; для контрагентов, по которым есть только старые item, при необходимости можно оставить поддержку старых типов в отчёте или показывать «нет взаиморасчётов» до первой новой транзакции «Долги».

### 3.6 Прочие места кода

- **Backend:** убрать `third_party_receivables` и `third_party_payables` из списков, связанных с планами погашения и цепочками (`item_plan_service.py`), если эти типы там использовались как «займы третьих лиц». «Взаиморасчёты» в планы погашения не включать.
- **Frontend:** во всех местах, где по типу определяют «долг третьих лиц» / «долг третьим лицам» (фильтры, подсказки, отчёты), перейти на использование `counterparty_settlements` или комбинации старого (для обратной совместимости) и нового типа по решению по п. 3.5.
- **Константы:** `ASSET_TYPE_CODES` / `LIABILITY_TYPE_CODES` на frontend — убрать коды `third_party_receivables` и `third_party_payables` из списков, используемых для выбора типа при создании актива. Для отображения и отчётов оставить маппинг названий и, при необходимости, список «все типы для отображения» с `counterparty_settlements`.

## 5. Риски и ограничения

- **Отрицательный баланс «Взаиморасчётов»:** логика и ограничения (лимиты, предупреждения) должны быть согласованы; сейчас для кредитной карты лимит задаётся `credit_limit`. Для «Взаиморасчётов» лимита в постановке нет — при необходимости можно добавить отдельно.
- **Валюта:** в постановке предполагается одна валюта (например, RUB) для «Взаиморасчётов» по контрагенту; мультивалютные взаиморасчёты могут потребовать отдельной доработки (несколько item по контрагенту по валютам или отдельная модель).
- **Редактирование/удаление «Взаиморасчётов»:** для пользователя недоступно (см. п. 3.1.3). Авто-закрытие при нулевом балансе и авто-открытие при ненулевом реализуются на backend при пересчёте баланса.
